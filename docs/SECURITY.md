# OfflinePay Security Protocol

This document outlines the cryptographic decisions and security architecture that enable trust in a zero-connectivity environment.

## Cryptographic Decisions

### 1. AES-256-GCM Encryption
OfflinePay uses **AES-256** (Advanced Encryption Standard with a 256-bit key).
- **Why 256-bit?**: A 256-bit key size offers $2^{256}$ possible keys, making brute-force attacks computationally infeasible even for quantum-assisted attackers.
- **Why GCM/CBC?**: We use Authenticated Encryption (GCM preferred, CBC fallback) to ensure that only the holder of the correct PIN can decrypt the transaction payload.
- **PIN-Derived Keys**: The encryption key is derived using a PBKDF2-like derivation from the user's secret PIN, ensuring sensitive data never touches disk in an unencrypted state.

### 2. SHA-256 Signatures
Every token includes a cryptographic signature generated using **SHA-256**.
- **Tamper Detection**: SHA-256 is highly sensitive; changing even a single bit in the transaction amount or recipient UPI ID will result in a completely different hash.
- **Authenticity**: By signing the JSON payload with a system-level secret, we ensure that tokens can only be generated by genuine OfflinePay clients.

### 3. Token Expiry (10-Minute Window)
All offline tokens carry an `expiresAt` timestamp set to 10 minutes from generation.
- **Replay Mitigation**: Limits the window of opportunity for an attacker to intercept a QR code and attempt to use it later.
- **Standard Alignment**: This 10-minute window aligns with standard banking and UPI token patterns, providing a balance between user convenience and security.

### 4. Device Fingerprinting
Tokens are cryptographically bound to the physical device through a `deviceId` fingerprint.
- **Anti-Screenshot**: A screenshot of a QR code stolen from one user cannot be used on a different device, as the signature verification will fail the hardware mismatch test.
- **Hardware Tie**: The fingerprint is derived from immutable hardware properties (User Agent + Screen Specs on web, Native IDs on mobile).

## Threat Model & Mitigations

### T1: Replay Attack
- **Scenario**: An attacker captures a QR code and scans it multiple times to drain a sender's balance.
- **Mitigation**: Every `txnId` is globally unique. The receiver app maintains a `usedTokens` store in IndexedDB. If a duplicate `txnId` is scanned, it is instantly rejected before any balance update occurs.

### T2: Token Interception (Man-in-the-Middle)
- **Scenario**: An attacker intercepts an SMS token or photographs a QR code in transit.
- **Mitigation**: The payload is encrypted with AES-256. Without the sender's PIN or the specific device fingerprint of the intended receiver, the intercepted data is useless noise.

### T3: Local Balance Manipulation
- **Scenario**: A malicious user modifies their local IndexedDB to artificially inflate their balance.
- **Mitigation**: The local balance is "optimistic." The **Backend API** is the source of truth. During the next synchronization, the server recalculates the ledger. If a discrepancy is found, the transaction is reversed, and the user's **Trust Score** is heavily penalized.

### T4: Double Spend
- **Scenario**: A user generates two QR codes for the same ₹500 balance and sends them to two different receivers before syncing.
- **Mitigation**: The app uses **Optimistic Locking**. Once a payment is authorized, the balance is locked/deducted locally. During sync, the backend processes transactions sequentially. If the second transaction exceeds the actual server-side balance, it is rejected, and the receiver is notified of the failed settlement.
